# 1. What is an LLM SDK?

**SDK** stands for **Software Development Kit**.

An **LLM SDK** is a library provided by an LLM provider that makes it easier for developers to communicate with an LLM from their application.

Instead of manually creating HTTP requests, an SDK provides ready-to-use functions and classes.

Conceptually:

```text
Without SDK:

Your Code
   ↓
HTTP Request
   ↓
LLM API
   ↓
Response


With SDK:

Your Code
   ↓
LLM SDK
   ↓
LLM API
   ↓
Response
```

---

# 2. Why Use an SDK?

An SDK simplifies communication with an LLM.

It can handle things such as:

* Authentication
* Request formatting
* API communication
* Response parsing
* Model interaction
* Error handling
* Provider-specific functionality

This allows you to focus more on building your application instead of manually managing HTTP requests.

# 3. LLM Provider vs SDK vs Model

These three concepts are different.

### LLM Provider

The company or service providing the model.

Examples:

```text
OpenAI
Google
Anthropic
```

### SDK

The programming library used to communicate with the provider.

Example:

```text
Python SDK
```

### Model

The actual AI model that processes the request.

Conceptually:

```text
Application
    ↓
SDK
    ↓
Provider API
    ↓
Model
    ↓
Response
```

# 5. API Key

Most LLM APIs require authentication.

An **API key** is a credential used by your application to authenticate with the provider.

Conceptually:

```text
Application
     ↓
API Key
     ↓
LLM Provider
     ↓
Allow API Request
```

Never hardcode API keys directly into source code.

Avoid:

```python
api_key = "my-secret-api-key"
```

Instead, store the key in an environment variable.

Example:

```text
OPENAI_API_KEY=your_api_key
```

Then read it from Python:

```python
import os

api_key = os.getenv("OPENAI_API_KEY")
```

---

# 6. Client

The **client** is the object used by your application to communicate with the LLM provider.

Conceptually:

```text
API Key
   ↓
Client
   ↓
LLM API
```

A client usually handles communication with the provider.

For example, an SDK may allow you to create something conceptually like:

```python
client = Client(api_key=api_key)
```

The exact syntax depends on the provider and SDK.

---

# 7. Model

An application usually specifies which model should process the request.

Conceptually:

```python
response = client.generate(
    model="model-name",
    prompt="Explain REST API"
)
```

The model determines the capabilities and behavior available to the application.

Different models may differ in:

* Reasoning capability
* Speed
* Cost
* Context window
* Output quality
* Multimodal capabilities

The exact available models depend on the provider.

---

# 8. Messages

Modern LLM applications commonly communicate using **messages** rather than only a single text prompt.

A conversation can contain different message roles.

The most common roles are:

```text
System
User
Assistant
```

Example:

```text
System:
You are a helpful programming assistant.

User:
Explain FastAPI.

Assistant:
FastAPI is a Python web framework...
```

---

# 9. System Message

The **system message** defines the general behavior or instructions for the model.

Example:

```text
You are a helpful Python tutor.
Explain concepts using simple English.
```

It can define:

* Role
* Behavior
* Rules
* Output expectations
* Restrictions

Example:

```text
System:
You are an AI course advisor.
Give concise and beginner-friendly recommendations.
```

---

# 10. User Message

The **user message** contains the user's actual request.

Example:

```text
User:
"What is FastAPI?"
```

The application receives this input and sends it to the model.

---

# 11. Assistant Message

The **assistant message** represents a response generated by the model.

Example:

```text
User:
"What is FastAPI?"

Assistant:
"FastAPI is a modern Python framework for building APIs."
```

Assistant messages can also become part of conversation history.

---

# 12. Message Flow

A simple conversation can look like:

```text

  ↓

  ↓

  ↓
User
  ↓

```

For example:


The application may send the relevant conversation history to the model.

# 13. Model Parameters

LLM APIs usually provide parameters that control how the model generates responses.

Common parameters include:

```text
Temperature

Model
```

The exact parameters depend on the provider and model.

---

# 14. Temperature

**Temperature** controls the randomness of model output.

A lower temperature generally produces more predictable responses.

A higher temperature generally allows more variation.

Conceptually:

```text
Low Temperature
      ↓
More predictable
```

```text
High Temperature
      ↓
More variation
```

For example:

### Low temperature

Useful for:

* Classification
* Extraction
* Factual formatting
* Consistent responses

### Higher temperature

Can be useful for:

* Creative writing
* Brainstorming
* Generating different ideas

The exact behavior and supported temperature range depend on the model.

---

# 15. Max Output Tokens

**Max output tokens** controls the maximum amount of output the model can generate.

For example:

```text
max_output_tokens = 200
```

means the application limits the generated output to the configured token budget.

Remember:

```text
Tokens ≠ Words
```

A token can represent part of a word, a complete word, punctuation, or other text fragments.

You learned tokens in **Week 02 — Day 01**.

API keys and other configuration values should normally be stored outside the source code.


Then your application can load it.

Conceptually:

```text
.env
 ↓
Environment Variable
 ↓

 ↓

```

# 21. Generic LLM Client Example

The exact SDK syntax differs between providers, so the following is a conceptual example:

```python
import os

api_key = os.getenv("LLM_API_KEY")

client = LLMClient(api_key=api_key)

response = client.generate(
    model="model-name",
    messages=[
        {
            "role": "system",
            "content": "You are a helpful programming tutor."
        },
        {
            "role": "user",
            "content": "Explain FastAPI."
        }
    ],
    temperature=0.2
)

print(response.text)
```

The important concepts are:

```text
API Key
   ↓
Client
   ↓
Model
   ↓
Messages
   ↓
Parameters
   ↓
Response
```

The actual class names and method names depend on the SDK you are using.

# 22. LLM Application with FastAPI

You already learned FastAPI in Week 03.

Now combine the concepts.

```text
Frontend
   ↓
POST /chat
   ↓
FastAPI
   ↓
Validate Request
   ↓
Build Messages
   ↓
LLM SDK
   ↓
LLM
   ↓
Response
   ↓
FastAPI
   ↓
Frontend
```

For example:

```python
@app.post("/chat")
def chat(request: ChatRequest):

    response = llm_client.generate(
        model="model-name",
        messages=[
            {
                "role": "system",
                "content": "You are a helpful AI assistant."
            },
            {
                "role": "user",
                "content": request.message
            }
        ]
    )

    return {
        "answer": response.text
    }
```

This is the basic foundation of an LLM-powered API.

# 24. Error Handling

LLM API calls can fail.

Possible reasons include:

* Invalid API key
* Invalid model name
* Rate limit
* Network error
* Timeout
* Invalid request
* Provider outage
* Token/context limits

The application should handle these errors properly.

Conceptually:

```text
LLM Request
     ↓
Try API Call
     ↓
Success ─────→ Return Response
     ↓
Failure
     ↓
Handle Error
     ↓
Return Safe Error Message
```

Do not expose sensitive internal errors directly to users.

# 26. Common Mistakes

### Mistake 1: Hardcoding API keys

Bad:

```python
api_key = "secret-key"
```

Use environment variables instead.

---

### Mistake 2: Confusing SDK and model

An SDK is the library used to communicate with a provider.

A model is the AI system generating the response.

```text
SDK ≠ Model
```

---

### Mistake 3: Sending only user input when system instructions are required

Applications often need a system message to define the model's behavior.

---

### Mistake 4: Ignoring errors

LLM API calls can fail, so production applications need proper error handling.

---

### Mistake 5: Sending unlimited conversation history

More context is not always better.

Large conversation histories can increase:

* Token usage
* Cost
* Latency
* Context pressure

The application should manage context carefully.

# 27. Interview Questions

### Q1. What is an LLM SDK?

An LLM SDK is a software library that simplifies communication between an application and an LLM provider's API.

---

### Q2. What is the difference between an SDK and an LLM?

An SDK is a programming library used to communicate with the provider, while an LLM is the model that processes inputs and generates outputs.

---

### Q3. What is a system message?

A system message provides high-level instructions that define the model's behavior, role, or rules.

---

### Q4. What is a user message?

A user message contains the user's request or input.

---

### Q5. What is an assistant message?

An assistant message represents the model's generated response and can also be included in conversation history.

---

### Q6. What does temperature control?

Temperature generally controls the randomness or variation of generated responses.

---

### Q7. What is max output tokens?

It defines the maximum amount of output the model can generate for a request, subject to the model and provider's limits.

---

### Q8. Why should API keys be stored in environment variables?

To keep sensitive credentials outside the source code and reduce the risk of accidentally exposing them.

---

### Q9. How does a FastAPI application communicate with an LLM?

A FastAPI route receives the request, prepares the input, uses an LLM SDK to call the provider's API, processes the response, and returns it to the client.
